## C. Current state of the backend

### C.1 Pipeline data flow

The four-stage pipeline (`backend/cron.js:43` → `runFullPipeline`) executes in order:

1. **Stage 1 — `pipeline/stage1_universe.js`**: Seeds the S&P 500 universe (~491 tickers after filtering acquired/delisted names like ANSS, CMA, DFS).
2. **Stage 2 — `pipeline/stage2_prescreen.js`**: For each ticker, calls `${SCRAPER_URL}/fundamentals/${ticker}`. Filters by market cap > $1B, drawdown ≥ 20%, revenue growth > 0%. After PR #107, throws explicitly on 20 consecutive scraper errors instead of breaking-and-returning-empty.
3. **Stage 3 — `pipeline/stage3_deepscore.js`**: For surviving candidates, calls `${SCRAPER_URL}/historical/${ticker}` and `${SCRAPER_URL}/fundamentals/${ticker}` again, runs the full TLI v2 score (50+ factors), writes to `screener_results`.
4. **Stage 4 — `pipeline/stage4_wavecount.js`**: Computes Elliott Wave count (the source of the constant fallback row), then calls `services/claude_interpreter.js` for narrative interpretation. Writes to `wave_counts`. Has daily Claude budget at line 12-22.

**All upstream data flows through the scraper service via `SCRAPER_URL`.** No file in `backend/services/` or `backend/pipeline/` reads from OpenBB or Polygon directly. Two exceptions: `services/fetcher.js` (the scraper client, mentions Polygon by name in comments) and `services/enrichment.js` (also mentions OpenBB in comments). Neither makes direct external HTTP calls — they go through the scraper.

**Anthropic API**: used for wave-count interpretation (`backend/pipeline/stage4_wavecount.js:7` imports `interpretWaveCount` from `services/claude_interpreter.js`). Daily budget tracked at lines 12-22 (`claudeCallsToday`).

### C.2 The wave-count fallback bug — documented

**Location**: `backend/services/elliott_wave.js`

**Trigger**: `validateImpulseWave(pivots)` at line 100 checks Rule 1 at line 111:
```javascript
if (p[2].price <= p[0].price) return {
  valid: false,
  reason: 'Wave 2 retraces beyond Wave 1 start',
  rule1_violated: true,
  still_in_correction: true,
};
```

**Constant row written**: At line 441-457 in the calling loop:
```javascript
if (!result.valid && result.still_in_correction) {
  results.push({
    ticker, timeframe: tf.label, wave_degree: tf.degree,
    wave_structure: 'impulse',
    current_wave: '2',
    wave_count_json: candidate,
    confidence_score: 25,
    confidence_label: 'SPECULATIVE',
    tli_signal: 'STILL_IN_CORRECTION',
    tli_signal_reason: 'Wave 2 breaking below Wave 1 start means this is not yet a new impulse wave...',
    entry_zone_low: null, entry_zone_high: null, stop_loss: null,
    target_1: null, target_2: null, target_3: null, reward_risk_ratio: null,
    last_updated: new Date().toISOString(),
  });
  continue;
}
```

**Behavior**: The fallback IS functioning as designed — it's an explicit "this isn't a new impulse wave yet" signal. The concern flagged in the audit brief is that this constant row may be appearing for **too many tickers**, suggesting either:
- Pivot-detection sensitivity (`tf.degree` / window slicing in the surrounding loop) is producing too many false-positive impulse candidates, OR
- The actual S&P 500 has many tickers in genuine corrective patterns and the fallback rate is genuinely high

Neither is a code bug. Recommended follow-up: count how many `screener_results` rows have `tli_signal = 'STILL_IN_CORRECTION'` vs other tiers, and if the ratio is implausibly high, investigate `detectPivots` sensitivity. **Do not "fix" by removing the fallback** — the fallback is correct; the question is whether the upstream pivot logic is over-firing.
